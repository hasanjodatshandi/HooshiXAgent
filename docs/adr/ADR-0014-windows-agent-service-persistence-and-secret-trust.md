# ADR-0014: Windows Agent Persistence and Secret Trust Model (LocalSystem Service)

Status: Accepted
Date: 2026-09-16

## Context

ADR-0010 decided the MVP Agent packaging/persistence model as user-scoped, with Windows implemented as a per-user binary plus a logon Scheduled Task, and explicitly recorded "Machine-scope Windows DPAPI plus LocalSystem service" as a rejected alternative "because it weakens/changes the accepted secret trust boundary" (`docs/adr/ADR-0010-packaging-deployment-and-release-trust.md`, Decision → "Agent packaging and persistence" and Alternatives).

A pre-launch audit found that the Windows product distribution actually built and deployed implements the rejected alternative, while the ADR, `README.md`, `docs/runtime/agent.md`, `docs/runtime/packaging-and-operations.md` and `packaging/agent/README.md` all describe the user-scoped model as if it were current. Two Windows persistence implementations therefore coexist in one repository, and documentation was not a truthful description of the shipped agent.

**The implemented service model**

`cmd/hooshix-setup` (`HooshiXAgent-Setup.exe`) installs:

- `hooshix-agent.exe`, `hooshix-agent-tray.exe` and `uninstall.exe` under `C:\Program Files\HooshiXAgent` (`cmd/hooshix-setup/setup.go:34-39`);
- the `HooshiXAgent` Windows service, running under the LocalSystem default account, configured for automatic start with `Tcpip`/`Dnscache` dependencies and restart-on-failure recovery (`internal/agent/svc/svc.go:282-328`, `internal/agent/svc/security.go:16-49`);
- machine-wide Agent state at `%ProgramData%\HooshiXAgent` (`internal/agent/state_dir_windows.go:13-18`), with the state tree DACL replaced by explicit grants before any secret is created (`cmd/hooshix-setup/setup.go:448-537`);
- an interactive desktop user tray auto-start task, run as that user with `InteractiveToken`/`LeastPrivilege` and no stored password (`cmd/hooshix-setup/setup.go:351-409`).

The service owns the complete Agent lifecycle, including the loopback pairing UI, so pairing works before any interactive logon (`internal/agent/svc/svc.go:3-9`, `:139-171`).

**What the DPAPI scope actually is (correction of the earlier label)**

The implementation is **not** machine-scope DPAPI. The runtime calls `CryptProtectData`/`CryptUnprotectData` with `dwFlags = CRYPTPROTECT_UI_FORBIDDEN` (0x1) and never sets `CRYPTPROTECT_LOCAL_MACHINE` (0x4) (`internal/agent/secrets_windows.go:13`, `:82-116`), and the store identifies itself as `windows-dpapi-current-user` (`internal/agent/secrets_windows.go:39`). The confidentiality policy note states the same explicitly: "DPAPI with CRYPTPROTECT_UI_FORBIDDEN under the CurrentUser scope, owned by the account that wrote the blob (LocalSystem for the service)" (`internal/agent/state_file_windows.go:14-23`).

So the secret blob is protected in the **user scope of the service account** (`NT AUTHORITY\SYSTEM`), not in machine scope. The change from ADR-0010's model is therefore materially smaller than ADR-0010's wording implies: what changes is *whose* user scope owns the blob, not the protection class. No other local user can unprotect it. What changes is that SYSTEM — and therefore any principal that can obtain SYSTEM, which includes local Administrators on a Windows host — is the owning scope.

**Why the user-scoped model is no longer sufficient**

An edge tunnel agent must serve its loopback services whenever the device is powered and on the network. The user-scoped model starts the Agent from a logon trigger in one interactive user's context, so on a device with no interactive logon session (a headless or unattended host, a host idling at the lock screen after a reboot, a device whose only user never logs in) no Agent runs and every assigned public route fails closed. That is a product-blocking limitation, not a preference. The service model also gives the Agent a machine-wide lifetime that matches its machine-wide role: one device identity, one tunnel, one state tree, independent of who is logged in.

The owner reviewed the finding and delegated this decision on 2026-09-16 with the direction that the ADR framework exists to record decisions truthfully, so the documentation and the delivered distribution must be made to agree with the decision rather than the ADR being silently ignored.

## Decision

The Windows Agent persistence and secret trust model is the **service model**:

1. **Persistence.** The Agent runs as the Windows service `HooshiXAgent`, installed by the supported Windows distribution and started by SCM, not by a logon trigger. It runs under the LocalSystem default service account. There is **no password-bearing service account**: `Install` creates the service without a `ServiceStartName`/password (`internal/agent/svc/svc.go:309-315`).
2. **State location.** Agent state is machine-wide at `%ProgramData%\HooshiXAgent`, resolved through `FOLDERID_ProgramData` rather than an environment variable (`internal/agent/state_dir_windows.go:13-18`, `cmd/hooshix-setup/setup.go:497-508`). The CLI follows the service identity: when a service installation owns state there, `DefaultStateDir()` selects that directory instead of a per-user path (`internal/agent/config.go:27-38`).
3. **Secret protection.** Secrets (the Ed25519 seed and the short-lived session token) are protected with Windows DPAPI in the **service account's user scope** under `CRYPTPROTECT_UI_FORBIDDEN`, and the containing state tree is ACL-restricted by the installer. This is **not** machine-scope DPAPI: `CRYPTPROTECT_LOCAL_MACHINE` is not set. ADR-0010's label "machine-scope Windows DPAPI plus LocalSystem service" did not describe the implementation and is corrected here.
4. **State tree ACL.** The installer replaces inherited ACEs on the state directory with explicit grants for SYSTEM, Administrators and the interactive desktop user only, and applies that DACL **before** the pairing capability or any service-created secret exists (`cmd/hooshix-setup/setup.go:448-537`). `pairing.capability` receives a tighter explicit ACL of its own (`cmd/hooshix-setup/setup.go:525-537`).
5. **Supported Windows distribution.** The supported Windows distribution channel for this Agent is the desktop service installer `HooshiXAgent-Setup.exe` produced by `scripts/build-setup.ps1` from `cmd/hooshix-setup`, which installs exactly the model above. Its shipment status is recorded below; it is no longer restricted — rollout step R5 made `HooshiXAgent-Setup.exe` part of the published release subject set on 2026-09-17.
6. **Tray is not Agent persistence.** The interactive-user tray auto-start task is a desktop UI affordance only. The Agent's tunnel does not depend on it, and the tray opens the service with least-privilege per-operation SCM rights rather than `SERVICE_ALL_ACCESS` (`internal/agent/svc/svc.go:34-44`, `internal/agent/svc/security.go:51-92`).
7. **One model per device.** A device must not run both the service model and the user-scoped logon-task model at once. Aligning the archive installer (below) is a required rollout step, not an optional one (that step, R1, was executed on 2026-09-17).

### Owner-approved remediation decisions recorded by this ADR

- **Dormant code-signing path removed; "unsigned MVP" accepted as a risk.** `scripts/build-setup.ps1` previously contained a signing step that silently returned unless `HOOSHIX_SIGN_CERT_PATH` was set, and no workflow ever set it, so the build looked signing-capable while every produced binary was unsigned. That dormant path was removed. The accepted risk for the unsigned MVP — SmartScreen/AV reputation warnings and no publisher identity, with integrity instead established by GitHub Artifact Attestations over `SHA256SUMS` that a consumer must verify explicitly — is accepted only for the pre-launch MVP and must be revisited before general availability (`docs/runtime/packaging-and-operations.md`, "Authenticode signing status (accepted risk)").
- **`Setup.exe` shipment was withheld pending signing (recorded 2026-09-16).** At that time the service-model distribution was built and verified to build, but was deliberately withheld from publication as a release artifact while the binaries were unsigned. This ADR therefore recorded an accepted, temporary gap between the *decided* Windows channel and the *published* one, with the rollout steps below as its closure path. **Rollout status (2026-09-17): that gap is closed — R5 was executed.** `.github/workflows/release.yml` now builds `HooshiXAgent-Setup.exe` in a dedicated `windows-setup` job on the verified release commit, `finalize` re-verifies that the installer embeds the released `hooshix-agent.exe` verbatim and folds it into the release `SHA256SUMS`, and `attest`/`publish` treat it as a first-class subject. The binaries themselves are still unsigned, so the accepted "unsigned MVP" risk recorded above now applies to a *published* artifact rather than only to a local build; that is the risk R6 revisits before general availability.

## Alternatives

- **ADR-0010's user-scoped model (per-user binary plus logon Scheduled Task, DPAPI CurrentUser under the interactive user).** Not selected: it cannot serve a device with no interactive logon session, and it gives one device a *per-user* identity and state tree while the Gateway authorizes the *device*. It would still be the better choice where Agent state must be provably isolated per human user on a shared/multi-session host, where the device is only meaningful while a specific user is logged in, or where installing a machine-wide privileged service is unacceptable (locked-down or unmanaged hosts). Those conditions do not describe the MVP device set.
- **Machine-scope DPAPI (`CRYPTPROTECT_LOCAL_MACHINE`).** Not selected and explicitly not implemented: with the local-machine flag any local user on the host can unprotect the blob, which is strictly weaker than every other option here. ADR-0010's rejection of this is endorsed; what ADR-0010 mislabelled was the service model, which does not use it.
- **Password-bearing service account running as the interactive user.** Not selected for the reason ADR-0010 gave: installer custody of that account's password is not acceptable. The service model avoids it by running under the LocalSystem default account with no stored credential.
- **Password-bearing or virtual low-privilege service account (for example a service SID or gMSA).** Not selected for the MVP. It would narrow which principal can unprotect the DPAPI blob from "SYSTEM and anything that can become SYSTEM" to that account alone, at the cost of re-deriving the state-tree ACL, the pairing-capability ACL, the tray's SCM rights and the service DACL together, plus re-verifying the install/uninstall path. It is a plausible future hardening under this ADR's rollback/revisit criteria rather than a change made here.
- **Keep both models and let the installer choose.** Not selected: two persistence mechanisms on one device would race for the same state directory and identity, both bind the fixed loopback pairing port, and the device would present an ambiguous authority to the Gateway.
- **Keep the service model but leave `%LOCALAPPDATA%` state.** Not selected: a per-user state tree cannot be the identity of a machine-wide service, and the service would have to choose an owner arbitrarily.

## Consequences

### Positive

- The Agent serves its assigned routes on an unattended device with no interactive logon session; agent lifetime is bounded by machine uptime rather than by a logon session.
- One device identity, one state tree and one tunnel per device, matching the Gateway's per-device authorization model.
- The secret trust boundary remains user-scope DPAPI with a private state directory; the same protection class as ADR-0010 chose, owned by the service account instead of the desktop user.
- No password-bearing account exists anywhere in the delivered model.
- The service self-heals: SCM restart-on-failure after 5 s plus the Agent's own bounded reconnect loop (`internal/agent/svc/security.go:12-49`, `internal/agent/svc/svc.go:76-106`).
- Documentation, ADR and the delivered distribution describe one model.

### Negative

- The Agent's identity is now protected by a machine-wide principal rather than a per-user one, which widens the set of local attackers who can reach it (see Security impact).
- Installing or altering the Agent requires elevation, so the Windows install/uninstall path is no longer a user-scoped operation.
- Two Windows persistence implementations still exist in the repository until the rollout steps below are executed, which is a live divergence risk and a real support hazard. **Rollout status (2026-09-17): R1–R3 are executed, so only the accepted service model is installed by either Windows channel.** The hazard is now bounded to migration: both the archive installer and its uninstaller delete a pre-existing legacy per-user task named `HooshiXAgent`, so a device upgraded from an early archive release cannot end up running both.
- The service adds machine-wide SCM/registry surface (service object, DACL, ARP entry, `Program Files` and `ProgramData` trees) that the user-scoped model did not have.

## Security impact

**What an attacker with local Administrator or SYSTEM on the device gains.** The complete device identity and the ability to act as that device: SYSTEM is the DPAPI-owning account and can unprotect `secrets.dpapi` directly, and a local Administrator can reach SYSTEM on a Windows host (`SeDebugPrivilege` token theft, service creation, or an equivalent technique) — DPAPI user-scope protection is not a defence against that principal. With the Ed25519 seed and the configured session token/authorization identifiers the attacker can authenticate to the Gateway as the device for as long as the external authorization remains valid, receive the device's tunneled traffic, and terminate active sessions by rotating the key (`hooshix-agent rotate`). This is device identity theft and it is not softened by anything in this ADR. Under ADR-0010's model the same attacker needed the desktop user's context or credentials; that is a real, if limited, increase in exposure for an attacker who already holds local Administrator.

**What another unprivileged local user gains: nothing, unchanged.** The DPAPI blob is protected in the service account's user scope, so another interactive user cannot unprotect it. The state tree DACL grants the interactive desktop user only read+execute (`cmd/hooshix-setup/setup.go:512-523`), which means that user can read `config.json` (device/authorization/token identifiers, locally owned endpoints, update channel — never the private seed or raw session token, per ADR-0009) and can read the `secrets.dpapi` ciphertext without being able to unprotect it. Note the unavoidable tail of this: on a multi-user host, "the interactive desktop user" is whoever the installer resolved from the active console session, and the pairing capability is readable by that user by design because it authorizes that user's pairing attempt. A different unprivileged user gains no access to any of it.

**Residual exposure of the tunneled services: unchanged by this ADR.** Public-side input still selects only an opaque `local_endpoint_id`; the Agent still resolves it through its own approved mapping and dials only `127.0.0.0/8`, `::1` or literal `localhost` (ADR-0009 clause, unchanged). A local Administrator already owns the loopback services themselves, so this ADR grants no new reach to them. Moving state to `%ProgramData%` does not expose anything to the public side: the state directory is not served, and the pairing UI remains loopback-only with a non-loopback listener explicitly refused (`internal/agent/webapp/webapp.go:662-678`).

**What is not claimed.** No compensating control in this ADR makes a compromised SYSTEM principal survivable, and nothing here should be read as device-identity protection against a local Administrator. The controls below reduce accidental exposure and privilege breadth; they do not change these three honest statements.

**Compensating controls verified present in the code today**

- **Least-privilege SCM rights for the tray.** The service DACL installed at install time grants SYSTEM and Administrators full control and interactive users exactly `SERVICE_QUERY_STATUS | SERVICE_START | SERVICE_STOP` — no change-config, delete, DACL write or user-defined control (`internal/agent/svc/security.go:51-92`, `:76-93`; held-constant assertion `internal/agent/svc/svc_test.go:94`). Each tray/tooling call opens the service with the single right it needs instead of `SERVICE_ALL_ACCESS` (`internal/agent/svc/svc.go:34-44`, `:397-415`).
- **State-directory ACL hardening applied before secret creation.** `installPairingCapability` runs before service install/start (`cmd/hooshix-setup/setup.go:97-105`), creates the state directory, recaptures ownership, then replaces inherited ACEs with explicit SYSTEM/Administrators full control plus interactive-user read+execute, and only then generates and writes the pairing capability (`cmd/hooshix-setup/setup.go:448-495`). The rationale for hardening first — that the `(OI)(CI)` grant would otherwise keep propagating read access to every later file, and that Go mode bits set no DACL on Windows — is recorded at `cmd/hooshix-setup/setup.go:472-481`.
- **Myopic, non-inheriting pairing-capability ACL.** `pairing.capability` gets its own `/inheritance:r` DACL: interactive user read, SYSTEM and Administrators full control (`cmd/hooshix-setup/setup.go:525-537`). The capability itself is 32 bytes of CSPRNG entropy, compared in constant time (`internal/agent/pairing_capability.go:19-25`, `:77-82`), is required on every pairing route (`internal/agent/webapp/webapp.go:108`), and rotates after a successful pairing (`internal/agent/webapp/webapp.go:507-538`).
- **Restricted state tree, not just the directory.** The recovery path rewrites owner and DACL together over the whole tree and grants only SYSTEM/Administrators full control plus interactive-user read+execute (`cmd/hooshix-setup/setup.go:545-602`); ownership and DACL are set in the same `SetNamedSecurityInfo` call precisely so an empty deny-all DACL cannot be installed (`cmd/hooshix-setup/setup.go:551-556`). Setting them separately is the failure this avoids.
- **Reparse-point and non-regular-file rejection.** State directories are validated component by component for reparse points (`internal/agent/state_file_windows.go:70-103`), and state files are opened with `FILE_FLAG_OPEN_REPARSE_POINT` and rejected if they are reparse points or directories (`internal/agent/state_file_windows.go:37-68`).
- **The runtime does not silently rewrite DACLs.** A previous helper widened permissions on every read (added ACEs, kept inherited ACEs, discarded the API return value) and was removed; the install-time ACL is authoritative and the agent only validates (`internal/agent/state_file_windows.go:14-35`, `:105-120`).
- **No password-bearing service account.** Service creation omits `ServiceStartName` and passes no credential (`internal/agent/svc/svc.go:309-315`).
- **Service recovery policy and dependency bounding.** Restart-on-failure with a one-day failure-counter reset and explicit `Tcpip`/`Dnscache` dependencies (`internal/agent/svc/security.go:12-49`, `internal/agent/svc/svc.go:309-323`). A failed startup exits non-zero so SCM recovery acts rather than presenting a hollow "Running" state (`internal/agent/svc/svc.go:60-74`).
- **Bounded diagnostics.** The service log is size-bounded and rotated with one retained previous file instead of growing without limit across reconnect loops (`internal/agent/svc/svc.go:175-181`, `:259-269`).
- **Payload integrity before anything reaches `Program Files`.** Every embedded payload binary is verified against the embedded `SHA256SUMS` before installation, and the deployed bytes are re-read and compared after the move so an AV/filter driver cannot silently substitute them (`cmd/hooshix-setup/setup.go:172-204`, `:232-243`).
- **Loopback-only pairing UI with port-squat detection.** The pairing listener refuses non-loopback addresses, and if the fixed port is unavailable it logs the possible squatting and moves to an ephemeral loopback port published in `pairing.endpoint.json` rather than handing the capability to a squatter (`internal/agent/svc/svc.go:148-163`, `internal/agent/webapp/webapp.go:662-678`).
- **Legacy plaintext credential removal.** The service deletes any legacy `token.txt` at startup so the credential exists only in the DPAPI store (`internal/agent/svc/svc.go:116-120`).
- **Uninstall protection against destructive or unowned targets.** State removal is fail-closed unless the target is a safe real directory carrying the versioned ownership marker, and uninstall handles SYSTEM-only DACLs from earlier builds explicitly (`cmd/hooshix-setup/uninstall.go:173-201`, `:318-334`; assertions `cmd/hooshix-setup/setup_test.go:123`, `:187`).

## Reliability/performance impact

The service is a single process per device with SCM-managed lifetime. Automatic start (not delayed) plus recovery actions bound the outage after a crash to roughly the 5 s restart delay, on top of the Agent's existing bounded 1–30 s reconnect backoff. Startup failure is reported to SCM as a failure so recovery applies. Cost is one resident agent process and one rotating log file per device, unchanged in shape from the user-scoped model apart from the owning account. Runtime limits, protocol bounds and Gateway behaviour are untouched by this ADR.

## Compatibility/migration impact

- ADR-0009's secret-storage clause — "On Windows, the secret payload is encrypted with DPAPI for the current user" — remains in force and is satisfied literally: the current user is the service account. No clause of ADR-0009 requires that user to be the interactive desktop user, so ADR-0009 is **not** superseded by this ADR. What this ADR changes is which account owns the current-user scope.
- ADR-0009 line "A later change to the identity algorithm, private-key ownership boundary, or secret-store trust model requires the applicable ADR process" is the clause this ADR discharges for the service-account ownership boundary.
- `agent.DefaultStateDir()` now resolves to the machine-wide directory whenever a service installation owns state there (`internal/agent/config.go:27-38`), so CLI use follows the service identity instead of creating a second identity under the operator's profile. `ServiceStateDir()` on non-Windows platforms still mirrors the per-user default (`internal/agent/state_dir_other.go:5-13`).
- The Windows Agent default state path is `%ProgramData%\HooshiXAgent` when the service model is installed, and remains the per-user path only when no service installation owns state.
- On-disk state format is unchanged; no migration of secret or config payload is required for a device that was installed with the service model.
- The archive installer was aligned to the accepted model by rollout step R1 (2026-09-17). `packaging/agent/windows/Install-HooshiXAgent.ps1` now defaults to `C:\Program Files\HooshiXAgent` plus `%ProgramData%\HooshiXAgent` and installs persistence through the Agent binary's own `service install`/`service start`; `Uninstall-HooshiXAgent.ps1` removes that service through the binary and fails if the registration survives. Both scripts still delete a legacy per-user logon task named `HooshiXAgent` as migration cleanup, so a device upgraded from an earlier archive release cannot end up running two Agents against one device identity.
- Linux (`systemd --user`) and macOS (LaunchAgent) persistence, the Gateway deployment, and the release/attestation pipeline are unaffected; independent processes with their own lifetime requirements and no equivalent "no interactive session" constraint in the MVP.

- `docs/engineering/executable-runtime-gate.md` registers gap G1, which is now recorded there as closed as a *defined* gate by `scripts/ci/windows-service-install-smoke.ps1` and as wired into the CI chain through the `windows-distribution-build` job.

## Rollout steps

These are the remediation steps this ADR recorded as required. **None of them was performed by this ADR itself**, which is a decision record; each is marked below with its status on 2026-09-17.

- **R1 — Align the archive installer to the accepted model. — DONE (2026-09-17).** As recorded at acceptance time, `packaging/agent/windows/Install-HooshiXAgent.ps1` then registered a per-user logon Scheduled Task for the Agent itself (`packaging/agent/windows/Install-HooshiXAgent.ps1:142-163`) and defaulted to `%LOCALAPPDATA%` (`:3-4`), with `Uninstall-HooshiXAgent.ps1` mirroring it. Both now install and remove the accepted service model instead: `Install-HooshiXAgent.ps1` defaults to `C:\Program Files\HooshiXAgent` plus `%ProgramData%\HooshiXAgent` and persists through `& $Target service install` / `service start` (requiring elevation, with `-NoPersistence` as the documented files-only mode), and `Uninstall-HooshiXAgent.ps1` stops and uninstalls the service through the binary first and throws if the registration survives. Both still unregister a legacy per-user task named `HooshiXAgent` as migration cleanup, so a Windows host cannot end up with both models.
- **R2 — Align the Agent persistence spec. — DONE (2026-09-17).** As recorded at acceptance time, `NativeServiceSpec` for `windows` emitted `schtasks.exe /Create /F /SC ONLOGON /RL LIMITED /TN HooshiXAgent ...` (`internal/agent/service.go:66-67`) and the Windows assertion pinned that string and explicitly rejected `sc.exe create` (`internal/agent/agent_test.go:252`). `internal/agent/service.go` now emits `sc.exe create HooshiXAgent binPath= "<binary>" service run-service start= auto DisplayName= "HooshiX Edge Agent" depend= Tcpip/Dnscache` plus `sc.exe failure HooshiXAgent reset= 86400 actions= restart/5000`, with the binary path deliberately carrying no `--state-dir` because the service resolves the machine-wide state directory itself. The Windows assertion in `internal/agent/agent_test.go` pins that output and rejects `schtasks.exe`, `ONLOGON` and `Scheduled`.
- **R3 — Align the smoke assertion. — DONE (2026-09-17).** As recorded at acceptance time, `scripts/ci/agent-install-smoke.ps1` asserted that the installed Agent's persistence spec matched `schtasks.exe` and `ONLOGON`, with the failure message "does not preserve the current-user Scheduled Task model". It now asserts `sc.exe create HooshiXAgent` and `start= auto` and throws if the spec matches `schtasks` or `ONLOGON`. The reason this step was deliberately left open at acceptance — that changing the assertion alone would make the smoke fail against a still-unmigrated installer — no longer applies, because R1 migrated that installer in the same change.
- **R4 — Close runtime-gate gap G1. — GATE IMPLEMENTED, EXECUTED ON AN ELEVATED REAL MACHINE, AND WIRED INTO THE AUTOMATED CI CHAIN; CI EVIDENCE PENDING THE NEXT WINDOWS RUN.** `scripts/ci/windows-service-install-smoke.ps1` is the gate: on an elevated Windows host it builds or accepts the real `HooshiXAgent-Setup.exe`, runs the real installer, asserts the observable accepted model, exercises SCM restart-on-failure, and asserts that the installed uninstaller removes the service, install tree, ARP entry, tray task and machine-wide state. It fails closed rather than skipping when it cannot run elevated. On 2026-09-17 an elevated real-machine run of the supported installer observed the accepted model end to end: `sc qc HooshiXAgent` reported `START_TYPE: 2 AUTO_START` with image path `"C:\Program Files\HooshiXAgent\hooshix-agent.exe" service run-service` and `SERVICE_START_NAME: LocalSystem`; `sc query` reported `STATE: 4 RUNNING`; `sc qfailure` reported `RESTART -- Delay = 5000 milliseconds`; the agent service process and `hooshix-agent-tray` were both running; `hooshix-agent.exe`, `hooshix-agent-tray.exe` and `uninstall.exe` were installed under `C:\Program Files\HooshiXAgent`; the `HooshiXAgentTray` task was registered for tray auto-start only; the ARP entry "HooshiX Agent" carried the installed `uninstall.exe --uninstall` string; `C:\ProgramData\HooshiXAgent` held the ownership marker, `pairing.capability`, `secrets.dpapi` and `status.json` with an ACL restricted to the interactive user (RX) plus SYSTEM (F) and Administrators (F); and uninstall exited 0 leaving no service, process, `Program Files` tree, tray task, ARP entry or state tree behind. Two limits are recorded with this step: the gate is invoked by the `windows-distribution-build` job in `.github/workflows/ci.yml`, which keeps its build-integrity steps and passes the distribution it already built via `-SetupExe`, but no workflow run has been observed since that wiring landed, so automated CI evidence for Windows service installation is pending the next Windows CI run rather than `Passed`; and the gate does not reboot the host, so reboot persistence is evidenced as SCM automatic-start configuration plus an observed restart-on-failure after a forced process termination, never as a literal physical OS reboot. `docs/engineering/executable-runtime-gate.md` section 7 records both.
- **R5 — Publish the accepted channel. — DONE (2026-09-17).** The first of the two options recorded for this step was taken: `.github/workflows/release.yml` gained the `windows-setup` job, which builds `HooshiXAgent-Setup.exe` on the verified release commit from the released `SHA256SUMS`; `finalize` re-verifies that the installer embeds the released `hooshix-agent.exe` verbatim, folds it into the release `SHA256SUMS` and SBOM/vulnerability scanning, and `attest`/`publish` cover it as a first-class release subject. The decided Windows channel and the published Windows channel are therefore the same one, and operator documentation no longer has to state a difference.
- **R6 — Revisit `Setup.exe` shipment and signing once Authenticode signing exists. — OPEN.** Windows binaries are still **not** Authenticode-signed: no signing step exists in `scripts/build-setup.ps1` or `.github/workflows/release.yml`, and the dormant signing path discussed above stays removed. Because R5 published the installer while the binaries remain unsigned, the accepted "unsigned MVP" risk (SmartScreen/AV reputation warnings, no publisher identity, integrity established only by the Artifact Attestations over `SHA256SUMS` that a consumer must verify explicitly) now attaches to a published artifact. Invoking this step still means obtaining a code-signing certificate, adding the signing step to both files, and gating the release path so a missing certificate fails the release instead of being skipped. The pre-general-availability revisit recorded in the accepted-risk clause above is unchanged and is now the outstanding item.

## Rollback/supersession

**Clauses of ADR-0010 superseded by this ADR:**

- the "Agent packaging and persistence" default-model clause, as it applies to Windows: "Default installation is user-scoped ... Windows: per-user binary plus a logon Scheduled Task" (`ADR-0010`, Decision);
- the corresponding claim "This preserves the existing Unix per-user state ownership and Windows DPAPI CurrentUser trust boundary. AG-7 does not change DPAPI to machine scope and does not require a password-bearing Windows service account" (`ADR-0010`, Decision) — in particular the assertion that the DPAPI trust boundary is unchanged for Windows;
- the rejected-alternative entry "Machine-scope Windows DPAPI plus LocalSystem service: rejected because it weakens/changes the accepted secret trust boundary" (`ADR-0010`, Alternatives), which both mislabels the implemented model and rejects it;
- the fitness function "Agent persistence specs do not cross the Windows DPAPI CurrentUser boundary" (`ADR-0010`, Verification), which as written forbids the accepted model;
- the compatibility sentence "A future system-wide Windows service design ... requires the applicable ADR/replan process" (`ADR-0010`, Compatibility/migration impact), which is discharged here.

**Clauses of ADR-0010 that remain in force:** everything else — Gateway Docker Compose deployment topology, Caddy/TLS trust and internal Caddy→Gateway verified TLS, operational observability endpoints and their exclusion from the public edge, release/update trust (checksum + Artifact Attestation), the no-Control-Panel/no-database/no-Kubernetes scope constraints, the remaining rejected alternatives, and the Linux/macOS user-scoped packaging model. ADR-0010 remains `Accepted` authority for those clauses; it is superseded by this ADR only for the clauses listed above.

Superseding this ADR requires a new Accepted ADR and any required Durable Plan change. Rolling back the decision itself means re-installing the user-scoped model on Windows and re-accepting the loss of unattended/headless service, which is not a supported configuration under this ADR.

**What would force revisiting this decision:**

- a requirement to serve a device that has no interactive logon session *and* must keep per-user identity isolation on a shared multi-session host, which the service model cannot satisfy;
- a decision to narrow the owning principal to a virtual service account or gMSA, which would reduce the local-Administrator exposure described in Security impact;
- evidence that device-identity theft by a local Administrator has become a real, exploited risk for the deployed device population (which would argue for hardware-backed key custody rather than a different DPAPI scope);
- the supported Windows distribution changing again — if the ZIP archive is retired or `Setup.exe` becomes the published artifact per R5, this ADR's distribution statement must be updated to match. **R5 was executed on 2026-09-17**, so this trigger has fired and the distribution statements in this ADR, `docs/runtime/packaging-and-operations.md`, `README.md`, `docs/runtime/agent.md` and `packaging/agent/README.md` now record `HooshiXAgent-Setup.exe` as the published Windows artifact, with the ZIP archive remaining the aligned archive channel rather than the superseded one;
- a Windows platform change that removes or restricts the LocalSystem default account, DPAPI user-scope protection, or the SCM dependency/recovery configuration relied on here.
